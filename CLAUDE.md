# CLAUDE.md

`shiny.val.tools` — R package producing per-feature validation artifacts for Shiny apps in pharma/GxP contexts, including modern rhino apps using `box`. Full design lives in `specs/`. Start with `specs/00-overview.md`, then `specs/05-public-api.md` for the suggested implementation order.

## Workflow: TDD, green check before moving on

For every meaningful increment — one exported behavior, one bug fix, one new warning code:

1. Write a failing `testthat` test under `tests/testthat/`.
2. Implement the minimum to pass.
3. Run `devtools::check()` (or `R CMD check`). Fix every error, warning, and note. Never move on without a clean check.

Test fixtures are small hand-built Shiny apps in `inst/extdata/`, each exercising a specific pattern (modules, `box::use`, hybrid imports, dynamic IDs, conditional `source()`). Add a fixture before the test that needs it.

For manual end-to-end checks against a real-world app, run against `D:\repos\shiny.explore`. That app is not part of the automated test suite — it is the user's sanity-check substrate when inspecting how artifacts look in practice.

## Specs are the source of truth

If implementation must diverge from a spec, update the spec in the same commit — never silently. If a spec is ambiguous, ask before guessing. The specs went through several rounds of pushback; treat them as deliberate.

## Stability contracts

Don't break these without a `schema_version` bump and migration note in the relevant spec:

- **`inventory.json`** (spec 03) is pinned at `schema_version: "1.0"`. Additive changes only within v1; never remove or rename fields. Downstream pharma tooling reads this.
- **Warning codes** — `SVT-W001..010` graph (spec 01), `SVT-W101..105` features (spec 02), `SVT-W201..206` inventory (spec 03) — are stable identifiers. Don't renumber, don't reuse retired codes. New codes append to the relevant range.
- **Determinism** — same source + manifest + package version → byte-identical artifacts. Hash-derived node IDs, sorted outputs, seeded layouts. Add a determinism test where it matters.

## Don't reinvent

Specs already chose dependencies deliberately: `renv::dependencies` + `pak::pkg_deps` for dep graphs, `testthat` for tests, `cli` for messages, `tibble` for tables, `visNetwork` for rendering, base R `parse()` + a hand-rolled visitor for AST. Don't substitute without updating the spec.

## Behavioral discipline

- **Think before coding.** State assumptions; ask if a spec is unclear; surface tradeoffs. Don't pick silently between interpretations.
- **Simplicity first.** Minimum code to pass the test. No speculative abstractions, no flexibility for callers that don't exist. If you write 200 lines and it could be 50, rewrite it.
- **Surgical edits.** Touch only what the failing test requires. Note unrelated dead code; don't delete it.
- **Comments only when the WHY is non-obvious.** Don't restate the code.

These bias toward caution over speed. For trivial changes, use judgment.

## What this package does not do

Full list in `specs/00-overview.md` non-goals; repeated here to prevent drift:

- Validate the app or its packages — we produce evidence; `riskmetric` / `val.meter` score; humans validate.
- Run the app — static analysis only, no `reactlog`.
- Trace beyond R — no JS handlers, no `www/`, no `htmlwidgets` internals.
- Diff across versions; multi-app analysis; auto-narrative documentation; monolithic reports.
